# 预约表单 UI 功能规格

> 状态：待用户确认
>
> 本文档只定义预约表单页及页内核对弹层。它不代表后端、数据库或真实提交已实现。

## 1. 本轮目标

为社群成员提供一个原生微信小程序入住预约表单界面，让用户可以：

- 选择入住日期和入住晚数；
- 填写入住人数、房间数量和联系信息；
- 在页内核对弹层中查看当前填写内容。

本轮的交付物是可在微信开发者工具中检查的前端流程演示，不是可以真正保存预约的业务版本。

## 2. 包含的功能

### 2.1 页面和视觉结构

- 顶部品牌与体验预约标题区域；
- 浅蓝背景、深棕色文字、白色圆角卡片、蓝色选中态和主按钮；
- 原生微信导航栏，不伪造返回按钮或右上角菜单；
- 使用现有猫咪和波浪线装饰资源，不将整张概念图作为整页背景；
- 采用现有内嵌字体样式，原生导航栏使用系统字体。

### 2.2 入住安排

- 当前入住日期展示；
- 页内月历弹层，支持上一月/下一月、选择日期、确认和取消；
- 选择 1 晚或 2 晚；
- 根据入住日期和晚数展示离店日期；
- 入住人数和房间数量加减控件；
- 加减控件的最小展示值为 1；
- 展示“双人房，每间最多入住 2 人”的提示。

### 2.3 联系信息

- 名字输入框，必填；
- 微信号输入框，必填；
- 备注输入框，选填，最多 500 字；
- 名字或微信号为空时，显示就地错误并保持格式表单页；
- 用户修改正确内容后，对应错误提示清除；
- 键盘弹出时，当前输入框应尽量保持可见。

### 2.4 核对弹层

- 展示入住日期、离店日期、晚数、人数、房间数量、名字、微信号和备注；
- 长备注可在弹层内滚动查看；
- 点击返回修改、关闭按钮或遮罩时关闭弹层；
- 返回表单后已填写内容保留；
- 使用明确的前端预览提示，避免让用户误以为预约已被保存或提交。

## 3. 明确不包含的功能

本轮不实现：

- 云函数；
- 数据库或任何持久化存储；
- 真实预约提交；
- 成功凭证页及凭证编号；
- 管理员通知、通知重试或通知状态；
- 用户登录、身份体系、历史预约或房态库存；
- 业务层面的日期资格校验、容量校验或双人房分配校验；
- 对现有 `miniprogram/pages/confirmation/` 凭证页的新增功能或重构；
- 上线发布、真实 AppID 配置和云环境配置。

## 4. 用户可见行为

1. 用户打开表单页时，页面展示演示默认值，包括当前日期、默认晚数、默认人数和房间数量。
2. 用户打开日期弹层后，弹层显示当前月的月历和当前暂存选择。
3. 用户翻月时，月历月份变化，已选日期不因翻月自动改变。
4. 用户选择日期后，弹层更新暂存选择和可读的日期标签。
5. 用户取消日期弹层时，表单中原来的入住日期不变。
6. 用户确认日期后，表单同步显示入住日期和离店日期。
7. 用户切换 1 晚和 2 晚时，离店日期及住宿摘要同步更新。
8. 用户减少人数或房间数量时，值不得低于 1。
9. 用户未填写名字或微信号就点击核对时，页面保持在表单，对应字段显示就地错误。
10. 用户填写必填字段后点击核对时，弹层展示当前表单内容。
11. 用户从核对弹层返回修改时，原有输入仍然保留。
12. 用户在 320px 和 375px 宽度下查看页面时，主要内容不应出现横向溢出。
13. 在本轮运行期间，页面的提示应始终说明这是前端预览，用户不应被告知预约已保存或已通知管理员。

## 5. 可逐条验证的验收标准

### 功能验收

- [ ] **AC-01** 当用户打开表单页时，页面应展示一组可继续操作的演示默认值，且不依赖后端请求。
- [ ] **AC-02** 当用户打开日期弹层时，系统应展示当前选中日期、月历、翻月操作和确认按钮。
- [ ] **AC-03** 当用户只翻月但未点击确认时，系统应保持表单中原日期不变。
- [ ] **AC-04** 当用户选择新日期并确认时，系统应更新表单的入住日期和离店日期摘要。
- [ ] **AC-05** 当用户切换入住晚数时，系统应按日历日期重新计算并展示离店日期，包括跨月、跨年和闰年场景。
- [ ] **AC-06** 当用户减少人数或房间数量且当前值为 1 时，系统应防止该值继续减少。
- [ ] **AC-07** 当用户输入名字、微信号和备注时，系统应在当前表单中保留这些输入，且备注最多接受 500 字。
- [ ] **AC-08** 当用户未填写名字或微信号并点击核对时，系统应显示对应的就地错误，且不展示核对弹层。
- [ ] **AC-09** 当用户完成必填字段并点击核对时，系统应展示包含当前日期、住宿安排、名字、微信号和备注的弹层。
- [ ] **AC-10** 当用户关闭核对弹层或点击返回修改时，系统应关闭弹层并保留原有表单输入。
- [ ] **AC-11** 当用户查看长备注时，弹层应提供可滚动的内容区域，不因文字过长破坏主要布局。
- [ ] **AC-12** 当页面在 320px 或 375px 宽度下渲染时，页面应保持主要内容可读且无非预期的横向溢出。
- [ ] **AC-13** 当用户在实际键盘下输入名字、微信号或备注时，当前输入控件应保持可见或可滚动到。
- [ ] **AC-14** 在本轮演示中，系统不得将任何用户操作表示为数据已保存、预约已提交或管理员已收到通知。

### 工程验收

- [ ] **AC-15** 所有注册在 WXML 中的事件处理函数都应存在对应页面方法。
- [ ] **AC-16** 页面不应新增云函数、数据库、本地持久化或网络请求。
- [ ] **AC-17** 修改文案后，生成字体样式的脚本应能重新生成 `font.wxss`，并报告缺失字符。

## 6. 允许修改的文件

### 允许修改

- `miniprogram/pages/reservation/index.js`：表单状态、日期与弹层交互；
- `miniprogram/pages/reservation/index.wxml`：表单及弹层结构；
- `miniprogram/pages/reservation/index.wxss`：页面样式、响应式布局、安全区和状态样式；
- `miniprogram/pages/reservation/index.json`：仅在页面配置确实需要时修改；
- `scripts/check-reservation.cjs`：为本轮新增或修正预约表单行为的检查；
- `miniprogram/styles/font.wxss`：仅通过 `scripts/build-font.py` 生成，不手动编辑；
- `README.md`：当手动验收方式或当前限制发生变化时同步更新。

### 不允许为本轮新增的范围

- `miniprogram/pages/confirmation/` 不属于本轮功能；
- 不新增云函数目录、数据库配置、登录配置或通知凭据；
- 不修改 `project.config.json` 以虚构真实 AppID 或云环境。

## 7. 自动检查和人工检查方式

### 自动检查

1. 在仓库根目录运行：

   ```bash
   node scripts/check-reservation.cjs
   ```

2. 修改 JavaScript 后运行：

   ```bash
   node --check miniprogram/pages/reservation/index.js
   ```

3. 修改 JSON 后，使用 Node 解析页面配置文件：

   ```bash
   node -e "for (const p of ['project.config.json','miniprogram/app.json','miniprogram/pages/reservation/index.json']) JSON.parse(require('node:fs').readFileSync(p)); console.log('PASS: JSON parse')"
   ```

4. 修改页面文案后，按仓库约定重新生成字体样式：

   ```bash
   /Users/aaaa/miniconda3/bin/python scripts/build-font.py
   ```

   检查脚本输出的缺字提示及 `miniprogram/styles/font.wxss` 是否被更新。

5. 对比当前 branch 与基线的 diff，确认只改动本 spec 允许的文件。

### 人工检查

1. 在微信开发者工具中打开项目，检查页面能否编译。
2. 以 375px 和 320px 宽度检查顶部、卡片、按钮和底部提示，确认无非预期横向溢出。
3. 完成日期弹层的打开、翻月、选择、确认和取消流程。
4. 检查跨月、跨年、闰日和 1/2 晚的离店日期。
5. 检查名字、微信号为空时的就地错误、焦点和弹层阻止。
6. 检查长备注、键盘、弹层滚动和返回修改后的输入保留。
7. 真机检查原生胶囊、底部安全区和字体显示。当前 `touristappid` 为占位值时，应记录为未验证，不得写成真机通过。

静态检查和 Node 状态测试不等于微信开发者工具编译、模拟器渲染或真机验收。这些结果必须分别记录。

## 8. 当前仍需我决定的问题

1. **核对弹层的“确认预约”按钮在本轮怎么处理？**
   当前本轮不允许真实提交、成功凭证或跳转到真实结果页，需决定是暂时隐藏该按钮、将其标记为预览操作，还是留在界面但不定义其后续行为。

2. **日期弹层是否应在界面上禁用当天和过去日期？**
   `plan.md` 将“当天和过去日期不能预约”列为业务规则，但当前 README 将日期资格校验排除在前端 UI 演示之外。需决定本轮只保留展示和计算，还是增加界面层禁用。

3. **“当前日期”的默认值是否始终按北京时间初始化？**
   当前前端代码按北京时间初始化，后续业务提交时还需由服务端重新校验。

4. **现有 `miniprogram/pages/confirmation/` 是否作为后续凭证功能单独管理？**
   本 spec 将其排除，但需确认它是否保留在当前 branch 中作为未来功能，或应移入另一个功能 branch。

5. **本轮是否需要验证“双人房容量”的界面提示？**
   `plan.md` 包含 `房间数 × 2 ≥ 人数` 规则，但本轮明确不实现业务校验；需确认是否只展示说明文字，还是引导用户不可能的组合。
